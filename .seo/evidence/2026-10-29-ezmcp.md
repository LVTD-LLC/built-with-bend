## Reproduction

Use a disposable directory and an isolated official Bend 2.0.38 Linux x64
release. The release archive's SHA-256 matched GitHub's release metadata:
`f19d088b079c9e1a8834ecd153b7d58c11a5f8f9ab1bdb78dbc96a6bf49aaa81`.
The managed compiler was not changed. All 40 files named by the six-package
`ez.lock.toml` matched their SHA-256 values in the isolated dependency cache.

At the pinned checkout, from `examples/demo`, the README's C-lane build
`bend main.bend -o demo` succeeded without source changes. No nix/ez global
installation was needed for this bounded demo. This is not a claim that every
repository check or every supported host works without that environment.

`./demo stdio` accepted initialize (revision 2025-06-18), initialized notification,
tools/list, and tools/call for add with a=2 and b=40. It returned structured
sum 42. A noninteger add argument returned a tool error; an unknown tool returned
JSON-RPC -32602. The process exited normally when stdin closed.

`./demo http PORT` was checked on loopback only. The same sequence returned
200 / 202 / 200 / 200, including sum 42. An untrusted Origin returned 403, an
unsupported MCP-Protocol-Version 400, and GET /mcp 405. The server was stopped
afterwards. No remote listener, external client integration or LLM call was used.

These observations do not verify every protocol revision, full conformance,
OpenAPI adapters, SSE client behavior, proof checking, benchmarks or security.
Source documentation, not this smoke, establishes the stated feature exclusions.
In particular, authorization is absent; keep local binding or an authenticating
proxy. Do not confuse client SSE response support with a server SSE stream.
